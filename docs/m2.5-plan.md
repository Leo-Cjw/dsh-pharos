## 2. 现状盘点

### 2.1 关键事实：两套「工作流」事件（已核实，勿混淆）

运行时里「工作流」事件分**两套、签名不同**，这是本方案最易踩的坑：

**① `tool-workflow/*` —— `session/event` 的 event.type**（不是独立 ctx.on 事件）

```
事件类型清单（session/event 的 event.type 全枚举）：
  "tool-workflow/agent-end", "tool-workflow/agent-start",
  "tool-workflow/run-end",  "tool-workflow/run-start", …
载荷：event.data.runId（匹配逻辑 String(event.data.runId)）
```
语义是「工具内部 workflow run 的生命周期（run-start → agent-start → agent-end → run-end）」，
用于 UI 的 workflow 节点进度条，**不是用户能感知的「后台任务阶段」** → **不接**。

**② `workflow/*` —— ctx.on 顶层 emit 事件**（本轮 B 组要接）

| 事件 | 签名（schema 原文） |
| --- | --- |
| `workflow/phase` | `'workflow/phase'(info: WorkflowRunInfo, title: string): void` |
| `workflow/log` | `'workflow/log'(info: WorkflowRunInfo, message: string): void` |
| `workflow/agent-start` | `'workflow/agent-start'(info: WorkflowRunInfo, agent: WorkflowAgentInfo): void` |
| `workflow/agent-end` | `'workflow/agent-end'(info: WorkflowRunInfo, agent: WorkflowAgentEndInfo): void` |

均为 `mode: 'emit'`（多参数），**与现有 `agent/*` 的 `(payload, meta, next)` 三参封装不兼容**
→ 需单独写订阅，不复用 `onAgentEvent` 包装。

### 2.2 ✅ 类型定义已全部核实（draft-1 头号风险已解除）

以下为 `app.asar` 内 TypeScript 声明原文（`declaration` 字段，逐字）：

```ts

    model?: string;
}

export interface WorkflowAgentInfo {
    seq: number;
    label: string;
    phase?: string;
    childId: SessionId;
}

export type WorkflowAgentOutcome = 'completed' | 'failed' | 'cancelled';

export interface WorkflowAgentEndInfo extends WorkflowAgentInfo {
    outcome: WorkflowAgentOutcome;
}
```

**对方案的三点直接影响**：

1. **✅ 会话归属可拿**：`WorkflowAgentInfo.childId: SessionId` —— agent 事件的
   `sessionId` 直接取 `childId`（真实会话 id），**不需要回退**。draft-1 的风险 #5 降级/删除。
2. **⚠️ `info` 不带 title/sessionId**：`WorkflowRunInfo` 只有 `id` + `meta`。
   → phase/log 事件（无 agent 参数）的会话归属只能回退 `String(info.id)`；
   → 人类可读标题取 `info.meta.name`（工作流名），阶段标题取 `title` 参数。
3. **⚠️ `WorkflowRunId` 是 branded string**：非数字、非 Symbol，`String(info.id)` 即其可读形式，
   可直接作 dedupeKey 的一部分（无需再解析结构）。

### 3.4 `silent` 帧机制（B-6，draft-4 新增）

**评审指出的问题**：draft-3 只写了「silent 通道」的想法，落地不了 ——
`makeFrame`（`frames.js:171-190`）解构字段里**没有 `silent`**，返回对象（:199-217）
也不展开它 → `dispatch({silent:true})` 会被静默丢弃（字段丢失，帧照发但没有标记）。

**定案修法（三处改动）**：

1. **`frames.js` — `makeFrame` 解构 + 条件展开**（与现有 `durationMs`/`tps` 同范式）：
   ```js
   // 解构区（:174-190）加两行
   subtype,
   silent,
   // 返回区（:213 之后）加两行
   ...(typeof subtype === 'string' ? { subtype } : {}),
   ...(silent === true ? { silent: true } : {}),
   ```
   同步更新 frames.js 顶部 doc comment 的帧形状清单（:10-12），
   增补 `subtype?` / `silent?` 两个可选字段。

2. **`host.js` — 在 handler 构造帧时传 `silent`，不在 dispatch 出口判断**：
   > 评审指出「在 `dispatch()` 出口按事件子类标记」表述含糊 —— `dispatch`（`host.js:98-104`）
   > 是通用出口（`makeFrame` → `bus.emit` → `emitWebhooks`），**它拿不到「子类」信息**。
   > 正确做法：`onLog()` 里 `dispatch({ subtype:'log', silent:true, dedupeKey:…, ... })`，
   > `onPhase/onAgentStart/onAgentEnd` 不传 `silent`（默认 false）。

> 🔴 **`interactionKey` 不是 `makeFrame` 的入参**（draft-7 修正，评审核实）：
> `makeFrame`（`frames.js:174-191`）的解构字段里**只有 `dedupeKey`，没有 `interactionKey`**
> —— 后者只是 `dedupeKeyOf(kind, sessionId, interactionKey)` 的**第三参名**（`frames.js:157`）。
> 若照 §3.9 早期写法把 `interactionKey:'log'` 塞进 `dispatch` parts，**会被解构静默丢弃**
> → 帧的 `dedupeKey` 回落默认值 `workflow:<sessionId>`
> → **同 workflow 的所有 phase 帧 dedupeKey 全相同 → 3000ms 内不同阶段互相吞掉**
> → 直接破坏 DoD「不同阶段互不吞」。
>
> **正确写法**：在 handler 里先算好，作为 **`dedupeKey` 字段**传入：
> ```js
> dispatch({
>   kind: 'workflow',
>   subtype: 'phase',
>   sessionId,
>   dedupeKey: dedupeKeyOf('workflow', sessionId, `phase:${title}`),  // ← 第三参在这里用
>   note, sessionTitle, agentType,
> });
> ```
> host.js 已 import frames.js 的若干函数（含 `noteFor` 等，见 `host.js:25-28`），
>    但**尚未** import `dedupeKeyOf`，需把 `dedupeKeyOf` 加入）。**§3.10 的写法本身就是对的**（interactionKey 是局部变量，
> 先传给 `dedupeKeyOf` 再把结果作为 `dedupeKey` 字段进 dispatch）—— 错的只是 §3.9/§3.4
> 把它误当成了帧字段名，两处不一致。**以 §3.10 为准。**
3. **`host.js` — 🔴 `emitWebhooks` 开头加 silent 判断**（draft-6 新增，评审抓出的实质漏洞）：

   > **漏点**：`silent` 只在浏览器半挡了（下面第 4 点），但 host 侧 `emitWebhooks`
   > （`host.js:105-119`）**没有任何 silent 判断**——完整链路是
   > `onLog → dispatch({silent:true}) → bus.emit（→ SSE 广播）→ emitWebhooks 无条件推送（:101）`。
   > **后果**：开 `workflowLog` 后 log 帧在浏览器端不弹了，却照样推给所有 webhook——
   > 只要该 webhook 勾了 workflow 事件（或 `events` 留空 = 全事件），
   > 企微/飞书/钉钉会被 log 帧刷屏，generic webhook 还会透传整帧。
   > 即「silent = 不打扰用户」只在浏览器成立，**webhook 侧照旧打扰**。

   ```js
   const emitWebhooks = (frame, config) => {
     const cfg = config;
     if (!cfg) return;
     if (frame.silent === true) return;        // ← 新增：silent 帧不外发
     if (cfg.skipSubagents === true && frame.agentType === 'subagent') return;
     if (isQuietNow(cfg, new Date())) return;
     ...
   };
   ```
   > 位置放在 `skipSubagents` 之前（最省，早退）。
   > ⚠️ 这是**语义决策**：`silent` = 「进 SSE 供调试，但**不打扰任何渠道**」。
   > 若日后需要「静默但仍要 webhook」，得另设字段（如 `silentLocally`）——本轮不做。

4. **`client.js` — `onSseFrame` 加 silent 分支 + `debug()` 加帧内容队列**：
   ```js
   // onSseFrame 内，kind 闸门之后、dedupe 之前
   if (frame.silent === true) { pushDebugFrame(frame); return; }  // 只入 debug，不弹通知
   ```
   > 🔴 评审指出 draft-3 §3.6⑥ 写「Debug 面板无需改动」与 §3.2「log 供 Debug 观察」
   > **自相矛盾**：现有 `debug()`（`client.js:782-798`）只有 `framesReceived`/`lastFrameAt`
   > **计数，没有任何帧内容队列** → silent 帧若只 return，什么都观察不到，等于白做。
   > 故 `debug()` 需加 `recentFrames: [...ring]`，容量取 **20 条**的环形缓冲，
   > 元素为 `{ kind, subtype, sessionTitle, note, ts }`（**不存整帧**，避免体积与敏感信息）。


**为什么 silent 帧仍要进 SSE 总线**：调试/排障时需要看到「host 确实收到并归一了 log 事件」，
这是可观测性的一部分；只是不打扰用户。

### 3.7 标题栏裸 id 的正解：修 `sessionTitle` 链路（draft-5 重做）

**评审纠正了 draft-4 的判断**：不该新增 `title` 字段。裸 id 的根因不是「缺字段」，
而是**浏览器半从头到尾没读 `frame.sessionTitle`**：

```js
// client.js:425（notificationFor 内）
const title = sessionTitle(sessionId);   // ← 自己查会话表
// client.js:262-267
function sessionTitle(sessionId) {
  const row = bindings.sessions.list.getSnapshot().byId[sessionId];
  return row && row.displayTitle ? row.displayTitle : sessionId;  // ← 查不到就返回裸 id
}
```

`grep frame\.sessionTitle lib/client.js` → **零命中**，证实评审属实。
而 host 侧本来就把工作流名写进了 `frame.sessionTitle`（`makeFrame` 默认 `'会话'`，
`frames.js:179`），且 `routes.js:146` 的 `JSON.stringify(frame)` **全字段透传** → 字段已到浏览器半，只是没人用。

**draft-4 加 `title` 字段的三处矛盾**（评审指出，确实成立）：
1. 与 `sessionTitle` **职责重叠** —— 两个字段都存「工作流名」；
2. §3.2 与 §3.7 对 `title` 的语义描述**自相矛盾**（阶段标题 vs agent label vs 工作流名）；
3. 与 §3.10 **直接冲突** —— dedupeKey 用 `title` 当 interactionKey：
   - 若 `title` = 工作流名 → 同一 workflow 的**所有 phase 全撞 dedupe**；
   - 若 `title` = 阶段标题 → 标题栏「工作流[阶段名]」+ 正文「进入阶段：阶段名」，阶段名**重复两次**。

**定案（删 `title`，只做两处小改）**：

1. **host**：workflow 帧的 `sessionTitle` 填 `info.meta.name`（已在 §3.2 写明）—— **零新增字段**。
2. **client**：`onSseFrame` 把帧的 `sessionTitle` 透传给 `deliver` 的 opts：
   ```js
   deliver(frame.kind, sessionId, note, { note, frameSessionTitle: frame.sessionTitle });
   ```
   `notificationFor` 的 workflow 分支优先用它：
   ```js
   } else if (kind === "workflow") {
     const wfTitle = opts.frameSessionTitle || title;   // 帧的 sessionTitle 优先
     notifTitle = t.workflowTitle;
     notifBody = t.workflowBody(wfTitle, note);
   }
   ```
   > 对其他 kind **保持现状**（仍走 `title` 查表），避免影响既有 6 类通知。

**去重的 interactionKey 另行取事件自带参数**（不依赖 `title` 字段，见 §3.10）。

### 3.8 订阅门：对齐 jobEvents 的双门（draft-4 修正）

**评审指出的问题**：draft-3 写的「无条件订阅 + dispatch 出口门」与 §3.3「类比 jobEvents」不成立 ——
真实机制是**双门**（实测 `host.js`）：
- 门 1：`host.js:372` —— `if (store.getConfig().jobEvents === true)` 才 `jobsService.events.subscribe(...)`
- 门 2：`host.js:315` —— `onJobEvent` 回调开头再判一次 `if (store.getConfig().jobEvents !== true) return;`

**评审指出的第二点**：无条件订阅会让「默认关时每次 log 仍触发回调」，开销白付。

**定案：对齐 jobEvents（关就不订阅）**
```js
// host.js apply() 内，仿 jobs 的写法
if (store.getConfig().workflowEvents === true) {
  subscribe('workflow/agent-start', onWorkflowEvent(onAgentStart));
  subscribe('workflow/agent-end',   onWorkflowEvent(onAgentEnd));
  subscribe('workflow/phase',       onWorkflowEvent(onPhase));
  // workflow/log 还要再叠一层 workflowLog（见 §3.9）
  if (store.getConfig().workflowLog === true) {
    subscribe('workflow/log', onWorkflowEvent(onLog));
  }
}
// 各 handler 开头再判一次（回调门，防运行中改配置）
const onPhase = (info, title) => {
  if (store.getConfig().workflowEvents !== true) return;
  ...
};
```

#### ⚠️ 双门是**不对称**的（评审纠正，draft-5 修正）

两门的生效时机不同 → **运行中改配置的效果方向相反**：

| 方向 | 订阅门（启动时） | 回调门（每次） | 实际效果 |
| --- | --- | --- | --- |
| 关（true→false） | 订阅**仍在** | 下次事件即 return | ✅ **即时生效** |
| 开（false→true） | **无订阅** | 收不到事件 | ❌ **需重启 DSH** |

⇒ 设置页提示文案**不能写**「改动需重启 DSH 生效」（对「关闭」方向是错的）。应写：
> **「开启需重启 DSH 生效，关闭即时生效」**

（与 `jobEvents` 现状对称，非本轮新增限制。）

### 3.9 `workflow/log` 高频的正解（draft-4 修正 B-6）

**评审指出的问题**：draft-3 的「静默只挡弹通知」只解决一半 —— log 帧**仍会**：
`makeFrame`（含 `randomUUID` + `noteFor` 字符串拼接）→ `bus.emit` → SSE 写帧（每客户端）
→ 浏览器 `onSseFrame` 全路径（dedupe + `sseSeen` Map 操作）。
风险 #3 只覆盖「若要弹」场景，没覆盖「默认关时的常驻开销」。

**定案（三层防护，默认根本不产帧）**：

1. **默认不产 log 帧**（主）：`workflowLog` 开关默认 `false`，
   且 `host.js` 里 **不订阅** `workflow/log`（同 §3.8 门 1）→
   默认情况下**零开销**（连回调都不进）。
2. **开启时限流采样**（次）：`workflowLog === true` 时，对 log 帧做 per-run 采样：
   ```js
   // 每个 info.id 每 N ms 最多产 1 帧（N = 5000）
   const LOG_SAMPLE_MS = 5000;
   const LOG_MAP_STALE_MS = 60 * 60 * 1000;   // 与 TURN_STATE_STALE_MS 同量级
   const lastLogAt = new Map();              // runId → ts
   const pruneLog = () => {                   // 仿 pruneTurns（host.js:128-133）
     const now = Date.now();
     for (const [runId, ts] of lastLogAt) {
       if (now - ts > LOG_MAP_STALE_MS) lastLogAt.delete(runId);
     }
   };
   const onLog = (info, message) => {
     if (store.getConfig().workflowLog !== true) return;
     const runId = String(info.id);
     const now = Date.now();
     pruneLog();                              // 每次回调前修剪，防无界增长
     if (now - (lastLogAt.get(runId) ?? 0) < LOG_SAMPLE_MS) return;
     lastLogAt.set(runId, now);
     // ⚠️ dispatch 的帧参数须写全（draft-5 曾用 `...` 省略，易漏字段）：
     //   subtype   —— 浏览器半分流与 debug 队列用
     //   dedupeKey —— ⚠️ interactionKey **不是 makeFrame 入参**（见下），必须先算成 dedupeKey
     //   silent    —— 不弹通知且不外发 webhook（§3.4 第 3 点）
     dispatch({
       kind: 'workflow',
       subtype: 'log',
       silent: true,
       dedupeKey: dedupeKeyOf('workflow', runId, 'log'),
       sessionId: runId,
       sessionTitle: info?.meta?.name || '工作流',
       agentType: 'root',
       note: message,
     });
   };
   ```
   → 开启后最坏情况 5s 一帧，可接受。
   > ⚠️ **Map 修剪（评审核实补充）**：以 `runId` 为 key 且**永不清理**会随 run 数累积。
   > 照 `pruneTurns` 的范式加修剪（`turnState` 也是这么做的，`host.js:128-133`）。
   > 另可在 `workflow/agent-end` 时删掉该 runId 的条目（更精确，但非必需）。
   > 🟢 **次要（评审认可可不改）**：`pruneLog()` 每次回调全量遍历 `lastLogAt`。
   > 因 Map 只含**活跃 run**（通常几个~几十个）且 log 已被 5s 限流挡住大部分，
   > 开销可忽略 → **本轮保持每次回调修剪**（最简、最不易漏）；
   > 若日后 Map 变大或成为热点，再仿 `pruneTurns` 移到低频点或加 size 上限。
3. **silent 标记**（末层保险，§3.4）：即使前两层漏了，也不弹通知。

> 评估：`silent` 机制**仍要实现**（B-6）——它是第 3 层保险，且对将来任何
> 「需要进 SSE 但不打扰」的帧都有用；但**主开关是「默认不订阅」**，
> 而非靠 silent 挡弹窗。

### 3.10 去重策略

workflow 帧的 `dedupeKey` **不能**用默认的 `workflow:<sessionId>`——相邻阶段/agent 会被
3000ms 去重窗吞掉。

> ⚠️ **写法澄清（draft-7，评审核实）**：`interactionKey` **不是 `makeFrame` 的入参**，
> 它是 `dedupeKeyOf(kind, sessionId, interactionKey)` 的**第三参**。
> 正确流程是 **「先算 → 再当 `dedupeKey` 字段传」**，
> **不是**把 `interactionKey` 当成帧字段名塞进 `dispatch` parts。

**第一步：handler 内按子类算出 interactionKey**
```js
// phase       → 阶段标题参数（天然唯一）
const ikeyForPhase = (title) => `phase:${title}`;
// agent-start → agent.seq（run 内序号）
const ikeyForAgent = (subtype, agent) => `${subtype}:${agent.seq}`;
// log         → 固定 'log'（log 无 seq/title，见下方说明）
const ikeyForLog = () => 'log';
```

**第二步：以 `dedupeKey` 字段进 dispatch**
```js
dispatch({
  kind: 'workflow',
  subtype: 'phase',
  sessionId,
  dedupeKey: dedupeKeyOf('workflow', sessionId, ikeyForPhase(title)),
  note, sessionTitle, agentType,
});
```
> ⚠️ `host.js` 需把 `dedupeKeyOf` 加入从 `./host/frames.js` 的 import
> （现 import 列表 `host.js:25-27` **不含** `dedupeKeyOf`）。
> ⚠️ 反面后果提醒：若误传 `interactionKey`（而非 `dedupeKey`），字段被 `makeFrame` 解构丢弃
> → 回落默认 `workflow:<sessionId>` → **同 workflow 所有 phase 帧互相吞**（§3.4 警示）。

- 同一 phase 重复上报仍去重（契约 §6「同事件不重复打扰」语义保住），不同阶段互不干扰。
- `interactionKey` 机制已存在于 `dedupeKeyOf(kind, sessionId, interactionKey)`（`frames.js:157-162`），
  直接复用，无需新造。
- 变量名用 `subtype` 而非 `kind`（评审指出 `${kind}` 与 `dedupeKeyOf` 第一参数 `kind`
  同名易歧义——虽然展开后语义正确，但读起来会误解为同一个值）。

> ⚠️ **log 的 interactionKey（评审核实补充）**：log 事件**没有 `seq` 也没有 `title`**，
> 若沿用 `${subtype}:${seq ?? title}` 会得到空串 → `workflow:<runId>:log:`
> → 同 run 的所有 log 帧在 host 侧 3000ms dedupe 全撞，**只发第一条**。
> 实际功能上靠 §3.9 的 5s 限流兜底（5s > 3s，故第一条后的 log 帧本就该被采样挡掉），
> 但语义隐晦。**定案：log 显式用固定 `interactionKey = 'log'`**（不依赖不存在的字段），
> 去重交给限流采样负责，语义清晰。
> 备选（不采用）：用 `message` 作 key —— 但旁白文本可能重复且很长，不适合做键。

> 🟡 **边缘情况（评审核实补充）**：phase 用阶段标题作 interactionKey，意味着
> **同一 workflow 若两次 `phase("相同标题")` 且间隔 < 3s，第二个会被 dedupe 吞掉**。
> 实际影响很小（同一 workflow 内连开同名阶段本就罕见），且被吞掉的是「重复信息」而非新信息，
> 故**接受**此行为、不额外加序号。仅在此备注，供日后有人遇到「阶段没提醒」时能查到原因。
